# Project Rosetta — Multi-Language / Multi-Framework Extension Plan
**For: coding agent execution**
**Goal:** add support for additional legacy source languages and additional target output frameworks, without ever weakening the currently-working Java → FastAPI path.

---

## 0. Non-negotiable ground rules (read first, apply to every step below)

1. **The certified path must never regress.** `getSubTotal` and `getTotalShipping` (and `getGrandTotal` once its extraction bug is fixed) are now the regression suite. Before and after every change in this plan, re-run all three. If any drops from PASS to FAIL, stop and revert — do not proceed to the next step.
2. **Fix trust in the current PASS signal before adding anything new.** Extending a pipeline whose validation can pass on a self-generated ("provisional") baseline just means new languages/frameworks inherit the same false confidence, at greater scale. Section 1 must ship first.
3. **Every new language or framework adapter is additive, never a replacement.** OFBiz-Java-to-FastAPI stays the default. New options are opt-in via explicit flags, never auto-selected.
4. **Every new adapter runs behind a try/fallback boundary.** If a new adapter throws, times out, or fails validation, the pipeline reports a clean, explicit failure for that adapter — it must never crash the run, corrupt state, or silently fall back to producing wrong output labeled as certified.

## 2. Architecture change: plugin boundaries for input and output

Right now, source parsing is hardcoded to `javalang` and output generation is hardcoded to FastAPI + SQLAlchemy. Both need a common interface so new languages/frameworks are additions, not rewrites.

### 2.1 Input side — `SourceAdapter` interface

```python
class SourceAdapter(Protocol):
    def parse(self, file_path: str) -> AST: ...
    def find_method(self, ast: AST, target_name: str) -> MethodNode: ...
    def extract_dependencies(self, method: MethodNode) -> list[Dependency]: ...
    def raw_source(self, method: MethodNode) -> str: ...
```

- Wrap the existing `javalang` logic as `JavaSourceAdapter` — this is a refactor of what already exists, not new logic. Run the regression suite immediately after this refactor alone, before adding anything else, to confirm the refactor didn't change behavior.
- Adapter selection driven by file extension + an explicit `--source-lang` flag (default: `java`), not auto-detection — auto-detection is a guessing step you don't need and it adds a failure mode.

### 2.2 Output side — `TargetGenerator` interface

```python
class TargetGenerator(Protocol):
    def generate_service_code(self, business_logic: dict) -> str: ...
    def generate_spec(self, business_logic: dict) -> str: ...
    def route_prefix_for(self, method_name: str) -> str: ...
```

- Wrap existing FastAPI + SQLAlchemy logic as `FastAPIGenerator` — same rule: refactor first, verify regression suite passes, before adding a second generator.
- Generator selection via `--target-framework` flag (default: `fastapi`).

### 2.3 Rules engine reuse
Your `rules/*.json` files already declare read/write patterns for Spring Boot, Java EE, Django, and Express/Mongoose — but nothing currently consumes them, since `javalang` only parses Java. Once `SourceAdapter` exists, these rule files become the natural per-language dependency-pattern config for their respective adapters. This is the fastest path to "support" (in the config-driven-recognition sense) — actual AST parsing for a new *language* (e.g. real Python or JS parsing) is separate, larger work; don't conflate the two.

## 3. Build order (sequenced, each step gated by the regression suite)

**Recommended priority — narrowest, highest-value addition first, not broadest:**

1. **Refactor to `SourceAdapter` / `TargetGenerator` interfaces**, wrapping existing Java + FastAPI logic exactly as-is. Verify regression suite still passes. *(No new capability yet — this step only proves the refactor was safe.)*
2. **Add Groovy as a second `SourceAdapter`.** This isn't a stretch pick — OFBiz genuinely mixes Java and Groovy service implementations, so this closes a real, already-flagged gap rather than adding speculative scope. Use Groovy's own AST (`groovy.ast` / a Groovy-AST-to-JSON bridge), not `javalang`. Test against one real Groovy-implemented OFBiz service, not a synthetic example.
3. **Add one new `TargetGenerator`** — recommend Express/Node.js, since it's the most different from FastAPI (different language entirely) and best demonstrates "framework-agnostic" isn't just a claim. Reuse the same `business_logic` IR — if the IR needs changes to support this, that's a signal the IR wasn't as language/framework-neutral as intended, which is itself useful information.
4. **Only after both land and pass regression:** consider a third adapter on either side, time permitting. Do not parallelize steps 2 and 3 across team members without the Section 1 fixes landing first — two people extending an unverified pipeline at once compounds the risk.

---

## 4. Fallback / circuit-breaker design

This is the part that protects the working demo path while the above happens.

1. **CLI default is unchanged.** `rosetta migrate --file X --target Y` with no extra flags must always resolve to `--source-lang java --target-framework fastapi` — the certified path — with zero behavior change from today.
2. **New adapters are wrapped in a try/except boundary at the orchestrator level**, not inside each adapter individually. If a `SourceAdapter` or `TargetGenerator` raises, or if validation fails 3x (existing retry cap), the CLI must print a clear `MIGRATION FAILED — <adapter name>` message and exit cleanly. It must never partially write artifacts and label them certified.
3. **Regression suite doubles as a pre-demo smoke test.** Before InnoFusion, run all three certified methods through the unmodified default path as the literal last check before presenting — if that's not green, present with the previous known-good recorded run (per the fallback approach already agreed for the live demo) rather than a live run on modified code.
4. **Feature-flag new adapters explicitly in code**, e.g. `SUPPORTED_SOURCE_LANGS = {"java": JavaSourceAdapter, "groovy": GroovySourceAdapter}` — adding a new adapter to this registry is the only integration point. This keeps "add a new language" from ever requiring touching the core orchestrator logic, which is what would put the working path at risk.

## 5. Definition of done for this extension

- [ ] Section 1 fixes shipped, regression suite passes with a **non-provisional** baseline
- [ ] `SourceAdapter` / `TargetGenerator` interfaces exist; Java + FastAPI refactored onto them with no behavior change (proven by regression suite)
- [ ] Groovy `SourceAdapter` passes on at least one real OFBiz Groovy service
- [ ] One new `TargetGenerator` (recommend Express/Node.js) passes on at least one already-certified method (e.g. `getSubTotal`), proving the IR genuinely generalizes
- [ ] Default CLI invocation (no flags) still produces byte-for-byte the same artifacts as before this work started
- [ ] A documented fallback: if any new adapter fails during the hackathon, the team can demo the original Java→FastAPI path with zero risk, on command
